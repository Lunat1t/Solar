# Стандарт разработки Solar 1.0

Это локальный инженерный стандарт проекта. Он использует официальные форматы Codex, но не является международной сертификацией или универсальным стандартом всех агентных систем.

## Термины и ответственность

- **Режим/роль**: текстовая инструкция. Файлы `.agent-workbench/roles/*.md` не создают сессии.
- **Нативный профиль агента**: `.codex/agents/*.toml`. Определяет имя, назначение, инструкции и sandbox будущей сессии.
- **Запущенный агент**: отдельная сессия, реально созданная runtime Codex. Наличие профиля не доказывает запуск.
- **Harness**: runtime Codex — агентный цикл, инструменты, управление контекстом, sandbox, события и subagent lifecycle.
- **Оркестрация**: создание задач/сессий, передача работы, ожидание результата и принятие решения о следующем действии.
- **Solar**: проектная конфигурация и рабочие правила поверх Codex, плюс утилиты проверок и запуска.

## Definition of Ready: когда можно начинать

1. У задачи есть наблюдаемый результат и критерии приёмки.
2. Известны область изменения и ограничения.
3. Есть исходный пример, воспроизведение или проверяемое требование.
4. Настроены конечные команды проверок и доступны зависимости.
5. Для длинной задачи записан план с проверяемыми промежуточными результатами.
6. Среда реально доступна; неизвестная возможность обозначена как blocked.

## Контракт передачи работы

Координатор передаёт каждому агенту цель, критерии, разрешённую область, исходные артефакты, зависимости и ожидаемый формат ответа.

Ответ содержит: статус `pass/fail/blocked`, что наблюдалось или изменилось, пути файлов, команды и фактические результаты, неизвестные условия, риски и следующий шаг. Статус не заменяет доказательства.

Независимые verifier/reviewer получают исходную задачу и фактические артефакты. Выводы исполнителя не подаются как установленная истина.

## Порядок работы

Координатор → explorer (наблюдения) → worker (реализация) → проверки координатора → verifier и reviewer (независимые отчёты) → исправление конкретных замечаний → повторная проверка затронутого поведения → приёмка.

Простой runner `run` создаёт последовательные CLI-процессы исполнителя и ревьюера. Он не использует нативную команду subagents.

`run-native` запускает координатора с просьбой создать четыре нативные сессии. Реальный spawn и результаты надо подтвердить по событиям/интерфейсу Codex. Python-скрипт не выдаёт факт запроса за доказанный запуск.

## Definition of Done: когда можно закончить

| Требование | Проверка |
|---|---|
| Все критерии задачи имеют наблюдаемые доказательства | Приёмка по артефактам |
| Настроенные проверки прошли на текущем состоянии | Автоматически: `check`, `fresh` |
| Последняя правка не сделала результаты устаревшими | Автоматически: отпечаток файлов и config |
| Нет неразобранных блокирующих замечаний ревью | Координатор/человек по отчёту |
| Проверен исходный сценарий и затронутые регрессии | Тесты и воспроизведение |
| Публичное поведение отражено в документации | Ревью diff |
| Факты, предположения и blocked-разделы разделены | Приёмка отчёта |
| В commit нет секретов и локальных журналов | Просмотр staged diff и Git ignore |

Команда `finish` автоматически проверяет только актуальность checks и наличие текста evidence. Остальные требования требуют разбора результатов. Нельзя называть их машинно обеспеченными.

## Правила изменений

- Сохранять существующие инструкции, настройки и чужие правки.
- Не расширять задачу без причины, вытекающей из критериев.
- У каждого изменяемого файла один ответственный исполнитель; параллельные писатели используют worktrees.
- Не ослаблять sandbox/доверие для обхода ошибки.
- Повторный провал требует новой проверяемой гипотезы, а не слепого повторения.
- Не публиковать и не сливать изменения автоматически.
- Модель наследуется из доступной среды; в исследованиях версия фиксируется явно.

## Воспроизводимость и исследование

Контроль и treatment используют одинаковые задачи и бюджеты. Данные held-out не передаются в обучение, steering и память. Помощь разработки отделена от исследуемого runtime. Причинность не выводится из одного объяснения агента.

## Проверка соответствия

Статические тесты подтверждают структуру TOML, наличие обязательных полей, sandbox профилей и сохранение существующей конфигурации при установке. Они не подтверждают, что установленная версия Codex распознаёт конфигурацию или реально запустила сессии.

Для живой проверки: запусти `codex --strict-config`, доверь проект, просмотри `/hooks`, создай маленькую задачу, выполни `run-native` и проверь отдельные сессии в `/agent` и события. Только после этого фиксируй live smoke test как пройденный.

Официальные источники: [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents), [Configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference), [Hooks](https://learn.chatgpt.com/docs/hooks).
