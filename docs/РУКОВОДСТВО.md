# Agent Workbench: переносимый сэтап разработки

Версия 1.0.0 · 5 октября 2026

Solar содержит проектный skill Agent Workbench и переносимый инструмент `agent_workbench.py`. Персональный skill в ChatGPT Work можно использовать дополнительно; он не является обязательной зависимостью репозитория. Skill помогает агенту пользоваться инструментом и адаптировать его к проекту. Инструмент добавляет правила, задачи, проверки, хуки, журналирование и управляемый запуск Codex.

Проверено: 18 автоматических тестов инструмента; независимая установка в Python-проект; успешная проверка, обнаружение внесённой ошибки и повторная успешная проверка после исправления. Оркестрация проверена с тестовой заменой CLI. Живой запуск модели через CLI в текущей среде не выполнен: здесь Codex CLI отсутствует. Активация нативных хуков требует действий в runtime на машине разработки.

## 1. Что говорил Илья Красинский

Это разбор его собственных открытых публикаций. Он не является транскриптом всего выступления или пересказом закрытого курса. Конкретные файлы и программы ниже — наша реализация, а не опубликованная им конфигурация.

**Harness как ввод в работу.** Красинский рассматривает каркас агента как перенос менеджмента: объяснение проекта, стандарты, критерии готовности и разбор причин ошибок. Каждый новый разговор без этого похож на работу сотрудника, которого не ввели в курс дела. Его оговорка: даже хороший каркас требует обучения и измерения исходов. [Публикация о harness](https://t.me/s/ilya_krasinsky?before=574).

**Сначала ожидаемый результат.** В его описании процессов проблема начинается с задач вроде «сделай дизайн»: между инструментами и людьми теряется контекст. Он предлагает следить за тем, что получено на входе и выдано на выходе, находить разрывы и добавлять перепроверку. [Заметки о процессах и агентах](https://t.me/s/ilya_krasinsky?before=433).

**Артефакты вместо впечатлений.** В тех же заметках он использует скриншот как пример наблюдаемого входа и результата. Для разработки наш эквивалент — воспроизводимый сценарий, diff и результат теста. Это адаптация его подхода: пиксельное совпадение само по себе не доказывает корректность программ.

**Повторяющиеся случаи превращать в реакции.** В перечне управленческих артефактов есть связи «когда X — делай Y», поиск разрывов и мест, где процесс создаёт себе дополнительную работу. Наши hooks применяют этот принцип к конкретным событиям исполнения.

**Пытаться опровергнуть качество.** В сентябрьской публикации он советует фальсифицировать утверждение, что агент сделал работу хорошо. Его Risk Assumption Test ищет разрывы между обещанием и поставкой, перегрузку команды и нехватку компетенций. Он также упоминает небольшие релизы для обратной связи и субагентов-критиков. [Публикации и промпт фальсификации](https://t.me/s/ilya_krasinsky?before=611).

**Ускорение требует выбора правильной работы.** В этом же источнике он предупреждает о ситуации, когда команда быстрее пишет код, а полезный результат не растёт. Для нас отсюда следует собственное правило: оценивать сэтап по результатам задач и затратам, а не по количеству агентов или инструментов.

## 2. Что находится в сэтапе

| Часть | Простое объяснение | Реализация |
|---|---|---|
| Skill | Повторяемая инструкция, как работать | Agent Workbench в твоих Skills |
| Harness | Условия, в которых работает агент | Codex плюс правила и инструменты проекта |
| Контракт задачи | Что должно получиться и где можно менять код | `.agent-workbench/task.json` |
| Оркестратор | Управляет исполнением, проверками и ревью | Команда `run` |
| Режимы работы | Инструкции под отдельный тип работы | plan, implement, debug, review, research |
| Hooks | Выполняются автоматически на событиях | `.codex/hooks.json` |
| Auto steering | Возвращает агента к задаче при явном сигнале | Повторный сбой, отсутствие актуальных проверок |
| Проверки | Запускают реальные команды проекта | Команда `check` |
| Журнал | Сохраняет результаты и ошибки | `.agent-workbench/runs/` |
| Checkpoint | Позволяет продолжить длинную работу | `.agent-workbench/checkpoint.md` |
| Изоляция | Разделяет изменения независимых исполнителей | Git worktree |

Режим работы — не постоянно запущенный отдельный агент. Оркестратор запускает исполнителя, а после успешных проверок — отдельного ревьюера с доступом только на чтение. Он останавливается для разбора ревью. Встроенных действий публикации или слияния нет.

## 3. Использование в ChatGPT Work

Открой боковое меню → Plugins → Skills. Там установлен Agent Workbench. Если список ещё не обновился, переоткрой страницу Skills.

В проекте можно написать:

> Используй Agent Workbench. Настрой его в этом проекте, проверь команды и зависимости, затем работай по этому сэтапу. Объясняй этапы простым языком.

Один установленный skill можно применять в разных проектах. Правила, команды и состояние задач каждого проекта остаются локальными для этого проекта. Настройка на подключённой машине возможна только если среда действительно доступна агенту.

## 4. Установка инструмента на Fedora или другой Linux/macOS

Требования: Python 3.11+, Git. Для `run` дополнительно нужны Codex CLI, вход в аккаунт и работающее подключение к модели. Python-часть не требует сторонних пакетов. Зависимости самого проекта устанавливаются отдельно по его lockfile.

Для переноса в другой проект используй самостоятельный файл `.codex/skills/setup-agent-workbench/assets/workbench/agent_workbench.py` или запускай корневой launcher из полного клона Solar. Корневой launcher зависит от файлов клона; отдельно переносить его нельзя. Выполни из Solar, заменив пример пути своим:

```bash
python3 agent_workbench.py --root /absolute/path/to/project init
```

Инструмент создаст `.agent-workbench/`, добавит собственный блок в `AGENTS.md` и собственные обработчики в `.codex/hooks.json`. Старые инструкции и группы хуков сохраняются. Конфликт с другой версией инструмента требует ручного разбора.

Перейди в проект и проверь состояние:

```bash
cd /absolute/path/to/project
python3 .agent-workbench/agent_workbench.py status
```

Если проект пока без Git, задачи и проверки работают, но хукам и CLI-оркестрации потребуется репозиторий. Создавай Git только в той папке, которая действительно является проектом.

Для установки Codex по официальной документации:

```bash
npm install -g @openai/codex@latest
codex --version
codex
```

Пройди вход через предлагаемый CLI способ. Затем в Codex открой `/hooks`, просмотри и доверь нужные определения. Доверие требуется runtime; наличие файла не означает активацию. Не применяй обход доверия. [Официальная установка](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex) · [Нативные хуки](https://learn.chatgpt.com/docs/hooks).

## 5. Адаптация к проекту

Открой `.agent-workbench/config.json`. Инструмент предлагает команды из известных манифестов: Node scripts, Python tests/Ruff/mypy, Rust, Go. Эти команды нужно сверить с проектом.

Пример блока для Python с pytest:

```json
{
  "checks": [
    {"name": "tests", "argv": ["python3", "-m", "pytest", "-q"], "timeout": 180}
  ]
}
```

Это пример замены поля checks, не всего файла. Не добавляй pytest, если в проекте другая система тестирования. При переносе конфигурации проверь путь к Python: автоопределение может сохранить абсолютный путь текущего интерпретатора.

Для Node проверяй, что `test` завершается, а не запускает watch mode. Для Vue полезны существующие команды lint/typecheck/test/build. У каждого проекта свои осмысленные проверки; переносимый сэтап не знает правильное поведение приложения заранее.

```bash
python3 .agent-workbench/agent_workbench.py check
```

Пустой список проверок считается отсутствием верификации. Ошибка, недоступная команда или таймаут дают провал. Нулевой exit code тестового процесса не гарантирует, что найдены тесты: это нужно проверить при настройке команды.

## 6. Обычный рабочий цикл

Создай конкретную задачу:

```bash
python3 .agent-workbench/agent_workbench.py task \
  --goal 'Исправить расчёт итоговой суммы' \
  --accept 'Пустой список даёт 0' \
  --accept 'Цена и количество учитываются во всех позициях' \
  --scope 'src/**' \
  --scope 'tests/**'
```

Scope объясняет разрешённые границы агенту; он не является системным запретом на чтение или запись файлов.

Далее агент воспроизводит проблему, делает правку и запускает проверки. Для длинной работы в checkpoint записываются цель, текущая гипотеза, результаты, препятствия и следующий шаг.

После изменений:

```bash
python3 .agent-workbench/agent_workbench.py check
python3 .agent-workbench/agent_workbench.py status
```

Результат считается актуальным только для текущей задачи, конфигурации проверок и состояния файлов. Последующая правка кода делает его устаревшим.

Для управляемого запуска через локальный Codex:

```bash
python3 .agent-workbench/agent_workbench.py run
```

Исполнитель → проверки → до двух исправлений после неудачи → проверки → независимое ревью. По умолчанию на каждый запуск агента даётся 900 секунд; у проверок свои таймауты. Эти параметры изменяются в config.

Результат `awaiting_review` означает, что нужно прочитать ревью и проверить критерии задачи. Успех процесса ревьюера сам по себе не равен одобрению кода.

После реального подтверждения результата запиши по одному доказательству на каждый критерий:

```bash
python3 .agent-workbench/agent_workbench.py finish \
  --evidence 'test_empty_cart прошёл: фактический результат 0' \
  --evidence 'test_multiple_items прошёл на нескольких позициях'
```

Команда требует актуальных успешных проверок и сохраняет переданные доказательства. Она не умеет самостоятельно определять правдивость текста доказательств. Завершённая задача перестаёт вызывать steering.

## 7. Auto steering

| Событие | Реакция |
|---|---|
| Начало сессии или новый запрос | Напомнить активную цель и критерии |
| Одна и та же команда дважды провалилась | Попросить пересмотреть причину |
| Агент завершает работу без актуальных проверок | Один дополнительный проход проверки/исправления |
| Проверка снова не выполнена | Сообщить о препятствии, без бесконечного цикла |
| Задача завершена | Перестать вмешиваться |

Сбой распознаётся только при наличии структурированного exit_code. Если runtime выдаёт другой формат, обработчик не выдумывает сигнал. Auto steering не видит мысли модели и не доказывает, что направление работы правильное. Он реагирует на конкретные наблюдаемые события.

## 8. Параллельная работа и Git hook

Для независимой задачи создай отдельное рабочее дерево:

```bash
python3 .agent-workbench/agent_workbench.py worktree \
  --branch feature/cart-fix \
  --path /absolute/path/to/cart-fix
```

Worktree берёт закоммиченное состояние. Незакоммиченные изменения исходной папки туда автоматически не переносятся. В каждом checkout — одна активная задача. Интеграция изменений и общая проверка остаются за координатором.

Для проверки перед commit:

```bash
python3 .agent-workbench/agent_workbench.py git-hook
```

Существующий pre-commit сохраняется: команду следует встроить в его менеджер. Этот hook проверяет рабочую папку, поэтому при частично staged изменениях отдельно проверяй именно будущий commit.

В существующий CI добавь ту же команду `check` после обычной подготовки окружения и установки зависимостей. Установщик не перезаписывает CI-пайплайны.

## 9. Amnesia и экспериментальная чистота

Сэтап разработки используется для написания экспериментального кода. Исследуемые агенты запускаются отдельно, с контролируемыми skills/hooks/memory.

`research_mode: true` отключает steering этого инструмента. Это не отключает другие глобальные хуки и навыки runtime. Для эксперимента нужны чистая среда, фиксированные версии, модель, бюджеты, разделение development/held-out и журнал всех попыток.

Бюджеты времени и повторов реализованы. Жёсткие ограничения токенов и долларов в версии 1.0 не реализованы. CLI event logs позволяют исследовать расход, но это не гарантированная отсечка по стоимости.

Архив Galaxy остаётся историческим материалом. Сэтап не переносит из него прежний движок или память. Никаких заключений о пользе Amnesia из проверки этого сэтапа не следует.

## 10. Где смотреть результаты и как отключить

Логи — `.agent-workbench/runs/`: stdout, stderr, exit code, длительность, результаты проверки, CLI events и ревью. Состояние задачи и checkpoint локальны. Не публикуй сырые логи без просмотра: команды могут вывести чувствительную информацию.

Для отключения нативного steering отключи группы Agent Workbench в `/hooks`. При удалении сохраняй чужие правила: убери только отмеченный блок в AGENTS.md, собственные группы из hooks.json и собственный необновлённый pre-commit. Изменённые другим инструментом файлы сначала разбери вручную.

Первый практический шаг: подключить реальную папку разработки, применить Agent Workbench, сверить проверки и доверить хуки в этом runtime. После этого можно начинать наблюдательные эксперименты Amnesia.
